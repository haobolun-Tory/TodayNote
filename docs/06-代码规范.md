# TodayNote 项目代码规范

## 1. 文档目标

本文档用于统一 TodayNote 项目的前后端代码风格、命名方式、结构约定与 AI 代码生成约束。

目标：

- 保证前后端代码风格一致。
- 降低多人协作时的理解成本。
- 避免 AI 每次生成代码风格不一致。
- 约束 AI 在生成代码前，先遵守本规范，再进行实现。

---

## 2. AI 使用约定

### 2.1 生成代码前置规则

每次使用 AI 生成、修改、补充代码时，默认先遵守本文档规范。

执行顺序要求：

1. 先理解当前需求。
2. 先检查是否符合本文档规范。
3. 再开始生成代码。
4. 生成后检查命名、结构、注释、异常处理是否符合规范。

### 2.2 AI 生成代码总原则

- 优先生成可读性高的代码，而不是炫技代码。
- 优先生成与当前项目技术栈一致的代码。
- 优先复用现有目录结构、命名方式和封装模式。
- 非必要不新增抽象层。
- 非必要不引入新依赖。
- 非必要不修改已有公共接口语义。
- 一次改动只解决当前目标问题，避免顺手大改。

## 3. 通用代码规范

### 3.1 基本原则

- 代码要清晰、稳定、可维护。
- 通过命名表达语义，尽量减少对注释的依赖。
- 函数职责单一。
- 模块边界清晰。
- 避免重复代码。
- 避免过长函数和过深嵌套。

### 3.2 命名原则

- 命名必须有业务语义。
- 不允许使用无意义命名，如 `data1`、`temp`、`obj`、`test`。
- 布尔变量应使用可判断语义，如：
  - `isPublished`
  - `isLoggedIn`
  - `hasPermission`
- 集合变量使用复数语义，如：
  - `articles`
  - `folders`
  - `comments`

### 3.3 函数设计原则

- 一个函数只做一件事。
- 函数长度尽量控制在 30 行以内，超过则考虑拆分。
- 参数过多时应考虑封装对象。
- 函数名要体现动作语义，如：
  - `loadArticles()`
  - `publishArticle()`
  - `validateFolderOwner()`

### 3.4 注释规范

#### 默认规则
- **默认不主动写注释。**
- 优先使用清晰命名、合理拆分和良好结构表达语义。

#### 允许写注释的场景
只有以下场景允许加注释：

1. 复杂业务规则。
2. 权限或安全边界说明。
3. 临时兼容逻辑或技术债说明。
4. 容易误解的特殊实现。

#### 禁止的注释类型
禁止生成无信息量注释，例如：

- `// 设置标题`
- `// 调用接口`
- `// 保存数据`
- `// 遍历列表`

#### 注释要求
- 注释必须解释“为什么”，而不是重复“做什么”。
- 注释必须与代码保持一致。
- 无效注释要删除，不保留历史垃圾注释。

### 3.5 异常与错误处理

- 不忽略异常。
- 错误信息必须可理解。
- 错误码、错误提示尽量与系统文档一致。
- 前端必须给出用户可理解的提示。
- 后端必须区分参数错误、权限错误、资源不存在和系统异常。

## 4. 前端代码规范

技术栈：Vue 3 + Vite + Vue Router + Pinia + Axios + Element Plus。

### 4.1 前端目录规范

推荐职责如下：

- `src/pages/`：页面级组件
- `src/components/`：通用组件
- `src/api/`：接口封装
- `src/stores/`：Pinia 状态管理
- `src/router/`：路由配置
- `src/assets/`：样式与静态资源

约定：

- 页面逻辑放在 `pages`
- 可复用 UI 放在 `components`
- 不在页面里直接写大量接口请求细节，统一放 `api`

### 4.2 Vue 组件规范

- 优先使用 `script setup`。
- 一个页面只负责当前页面场景。
- 可复用内容抽成组件。
- 页面不要堆积过多业务逻辑，应将通用逻辑下沉到组合函数、store 或 api 层。

### 4.3 组件命名规范

- 页面文件使用 PascalCase，例如：
  - `ArticleList.vue`
  - `ArticleDetail.vue`
  - `FolderManage.vue`
- 组件名应体现业务含义。
- 不使用无意义组件名，如：
  - `Test.vue`
  - `Demo.vue`
  - `Temp.vue`

### 4.4 状态管理规范

- 全局共享状态才放 `Pinia`。
- 页面局部状态优先使用 `ref` / `reactive`。
- 不把所有状态都塞进 store。

适合放入 store 的数据：

- 当前用户信息
- Token
- 全局登录态
- 未读通知数
- 全局筛选条件

不适合放入 store 的数据：

- 某个页面临时弹窗开关
- 某个表单局部输入状态
- 单页面一次性列表加载状态

### 4.5 API 封装规范

- 所有接口统一放在 `src/api/`。
- 接口命名要体现业务动作。
- 不在页面中直接拼接复杂请求逻辑。

示例命名：

- `getMyArticles`
- `getPublicArticles`
- `createArticle`
- `publishArticle`
- `createComment`

### 4.6 页面交互规范

- 用户可执行操作必须有明确按钮。
- 删除、取消发布等危险操作必须二次确认。
- 提交中要有 loading 状态。
- 接口失败要有错误提示。
- 空列表要有空状态展示。

### 4.7 表单规范

- 表单字段要有明确标签或占位提示。
- 提交前做基础校验。
- 错误提示要直观。
- 禁止出现提交后无反馈。

### 4.8 样式规范

- 优先复用 `Element Plus` 组件能力。
- 公共样式放全局样式文件。
- 页面局部样式使用 `scoped`。
- 不写大段重复样式。
- 颜色、间距、圆角尽量统一。

### 4.9 前端禁止事项

- 不在页面里直接硬编码大量模拟数据。
- 不在多个页面重复写同样的接口逻辑。
- 不滥用全局状态。
- 不把一个页面写成超大组件。
- 不默认生成大量无意义注释。

## 5. 后端代码规范

技术栈：Java 21 + Spring Boot + MyBatis-Plus + MySQL + JWT。

### 5.1 分层规范

后端按以下分层组织：

- `controller`：接收请求、参数校验、返回结果
- `service`：业务规则、状态流转、权限判断
- `mapper`：数据库访问
- `entity`：实体对象
- `dto`：输入参数对象
- `vo`：输出结果对象
- `common`：通用返回、异常、公共能力

约定：

- `controller` 不写复杂业务逻辑。
- `service` 不直接承担 HTTP 语义。
- `mapper` 不承载业务规则。

### 5.2 Controller 规范

- 只做请求接入、参数接收、简单校验、调用 service、返回结果。
- 不直接写复杂查询拼装逻辑。
- 不直接写权限核心逻辑。
- 接口路径命名尽量保持 REST 风格。

### 5.3 Service 规范

- 业务逻辑放在 `service`。
- 权限判断放在 `service` 或明确的权限辅助类中。
- 状态流转统一在 `service` 处理。
- 一个 service 方法聚焦一个业务动作。

示例：

- `createArticle()`
- `publishArticle()`
- `unpublishArticle()`
- `commentArticle()`

### 5.4 DTO / VO 规范

- 请求参数使用 DTO。
- 返回结果使用 VO。
- 不直接把数据库实体原样暴露给前端，除非场景非常简单且明确。
- DTO / VO 命名要体现用途。

示例：

- `ArticleRequest`
- `CommentRequest`
- `ArticleDetailVO`
- `ArticleSummaryVO`

### 5.5 Entity 规范

- Entity 与数据库表结构对应。
- 不在 Entity 中堆积业务逻辑。
- 字段名与数据库映射关系要清晰。
- 逻辑删除、自动填充等框架能力可以在 Entity 配置，但不写业务判断。

### 5.6 异常规范

- 业务异常使用统一业务异常类型。
- 参数错误、权限错误、资源不存在要区分。
- 不随意抛裸 `RuntimeException`。
- 异常信息要可用于前端提示或日志排查。

### 5.7 数据访问规范

- 优先复用 MyBatis-Plus 能力。
- 简单 CRUD 使用基础能力。
- 查询条件复杂时再扩展自定义 SQL。
- 不在 mapper 中写和业务强绑定的脏逻辑。

### 5.8 权限与安全规范

- 所有写接口必须校验登录态。
- 作者操作必须校验资源归属。
- 草稿访问必须校验是否为作者本人。
- 评论、点赞、收藏、关注等操作必须先校验目标资源状态是否合法。
- 敏感逻辑优先在 service 层统一控制。

### 5.9 后端禁止事项

- 不把业务逻辑堆在 controller。
- 不在多个 service 中复制同样的权限校验逻辑。
- 不直接把草稿暴露给公开接口。
- 不返回含糊错误信息。
- 不默认生成无信息量注释。

## 6. 数据库与接口规范

### 6.1 数据库字段规范

- 表名、字段名统一采用下划线风格。
- 时间字段统一使用：
  - `created_at`
  - `updated_at`
  - `deleted_at`
- 布尔 / 状态字段命名要清晰。
- 高频查询字段建立索引。

### 6.2 状态字段规范

- 状态值统一使用明确枚举语义。
- 如文章状态使用：
  - `DRAFT`
  - `PUBLISHED`
- 禁止使用魔法值表示状态。

### 6.3 接口返回规范

统一返回结构：

- `code`
- `message`
- `data`

约定：

- 成功返回码：`0`
- 参数错误：`40001`
- 未登录：`40100`
- 无权限：`40300`
- 资源不存在：`40400`
- 状态冲突：`40900`
- 系统异常：`50000`

## 7. 代码审查检查项

每次提交代码前，至少检查：

### 通用检查
- 命名是否清晰。
- 是否有重复代码。
- 是否有无意义注释。
- 是否存在过长函数。
- 是否有无用代码未删除。

### 前端检查
- 页面是否拆分合理。
- 接口是否统一封装。
- 是否有 loading / 空状态 / 错误提示。
- 是否误把局部状态放进全局 store。

### 后端检查
- controller 是否过重。
- service 是否承载完整业务逻辑。
- 是否做了权限判断。
- 是否正确区分公开域与作者域。
- 是否使用统一异常与错误码。

## 8. AI 代码生成执行语句

后续在项目开发中，可默认将以下规则作为 AI 生成代码前置要求：

> 先阅读并遵守 [docs/06-代码规范.md](docs/06-%E4%BB%A3%E7%A0%81%E8%A7%84%E8%8C%83.md)，再生成或修改代码。默认不添加无意义注释，优先使用清晰命名、合理拆分和统一分层结构实现需求。

---

## 9. 总结

本规范的核心目标只有三点：

1. **统一风格**：前后端代码保持一致性。
2. **降低维护成本**：优先靠结构和命名表达含义。
3. **约束 AI 输出**：AI 生成代码时，先遵守规范，再输出实现。

今后若项目新增技术栈或团队有新的协作约定，可继续补充本文档。
